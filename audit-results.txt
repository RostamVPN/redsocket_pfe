## 1. Executive Summary

redsocket_pfe is a small Rust program (about 2,350 lines, one dependency) that takes over a NIC queue on a cloud instance with AF_XDP, rewrites the cloud-NAT private destination of each arriving packet back to the public address (EIP), wraps it in GRE (or FoU) toward an exit host and transmits it; the exit answers clients directly with the EIP as source (direct server return, DSR). The companion script `deploy/backend-dsr.sh` configures the exit host. The threat model is a state-level network operator seeking to deanonymize users, block the service, or turn its infrastructure against private networks.

Overall risk posture: MODERATE. The forwarding core is narrow and sound — only packets whose destination is in the operator's map are forwarded, parsing is bounds-checked, the map reload is atomic and fail-safe, the dependency surface is one vendored crate with no advisories. The two issues raised against the earlier revision of the exit-host script (an allowlist that matched nothing, and an open relay through GRE plus IP forwarding) have been addressed in this tree: the allowlist now matches the real ingress device and the EIP set, and forwarding is disabled per tunnel device. The remaining risk is concentrated in (a) the tunnel being unauthenticated so that every protection lives in exit-host configuration, (b) that configuration being non-persistent, non-transactional and undone by routine host operations, and (c) debug logging that records every client's real IP address per packet — while the README's own example command enables it.

Findings: 0 Critical, 0 High, 4 Medium, 8 Low (12 total). No finding gives a remote attacker code execution or a silent plaintext leak of client traffic beyond what the design already carries (client-to-exit traffic transits the tunnel leg as sent by the client).

Top three issues:
1. RVPN-PFE-004 — `-d` logs each client source address per forwarded packet to the journal; `-dd`/`-ddd` dump packet bytes. README line 37 shows `-d` in the front-end start command. On a cloud instance this is a timestamped deanonymization record obtainable by the provider or by legal process.
2. RVPN-PFE-003 — the exit-host allowlist the README calls "mandatory" is not persisted by anything in the tree and is rebuilt non-atomically (the old table is deleted before the new rules exist), so a reboot or a failed re-run exposes every listener on the exit through every EIP.
3. RVPN-PFE-001/002 — GRE carries no key or MAC, so anyone who can forge an outer source equal to an EIP is indistinguishable from the front-end; the relay protection that contains this is a per-device IPv4 sysctl that the kernel resets whenever `net.ipv4.ip_forward` is flipped, with no netfilter forward policy and no IPv6 control.

Headline recommendation: make the exit-host controls durable and explicit (a firewall ruleset loaded as one transaction, with a forward-hook drop for tunnel devices, persisted devices and sysctls, IPv6 disabled on tunnels), remove `-d` from the documented command and gate per-packet logging behind a separate flag, and plan an authenticated encapsulation between front-end and exit (GRE key as a stop-gap; ESP/NAT-T or equivalent as the target).

### 2.4 Attack surface from manifests and build configuration
Inputs: (1) raw Ethernet frames on the bound queue — untrusted, from the whole Internet via the cloud NAT, plus the local L2 segment (ARP); (2) the map CSV at `--mapfile` — trusted, root-owned, re-read on SIGHUP; (3) argv and environment via the unit — trusted; (4) `/proc/net/route`, `/proc/net/arp`, `/sys/class/net/*` — trusted. Outputs: encapsulated frames to one gateway MAC, ARP replies for mapped private IPs, stdout (journal). Privileges: root with bounding set `CAP_NET_RAW CAP_NET_ADMIN`, unlimited locked memory; raw `bpf(2)`, `AF_XDP`, `AF_NETLINK` (RTM_SETLINK), one `AF_INET` UDP socket (neighbor.rs:73, route selection only). Exit host: GRE devices with no key, EIPs as local /32s, `rp_filter` off globally, `accept_local` on the ingress NIC, forwarding off per tunnel, an `inet` input-hook allowlist. The map file is the only policy object; there is no control plane, no network listener and no management API.

### 2.5 Scope-area notes (adapted checklist)
1. Forwarding integrity. The XDP program redirects every frame on the netdev to the socket (xsk.rs:712-720); frames the kernel accepts for the bound queue reach `handle_frame`. ARP: requests for a mapped private IP are answered (main.rs:474-492); replies are counted and dropped (:468-471); everything else is dropped. IPv4: destination looked up in the map (:508); non-mapped destinations are dropped, not forwarded (:510-514) — non-mapped traffic cannot be forwarded. Mapped destinations are forwarded regardless of protocol, port or source (:524-578); filtering is delegated entirely to the exit allowlist (README:107-109). The "black hole" property is therefore: the kernel never sees the queue's traffic and pfe forwards only mapped destinations — but it affects the whole NIC, not one queue (RVPN-PFE-007). GRE vs FoU: GRE header is `flags=0, proto=0x0800` (packet.rs:283-286); FoU is UDP with src=dst=map port and checksum 0 (:265-271); FoU is the CLI default (main.rs:71) although the README says a kernel back-end cannot decapsulate it (README:66-69) — RVPN-PFE-005. Fragments are mishandled (RVPN-PFE-008); inner sources are not validated (RVPN-PFE-009). Checkpoint: no path forwards unmapped traffic; open question whether FoU should remain selectable.
2. Authentication of the tunnel. None exists: no GRE key/sequence/checksum (packet.rs:277-287), no `key` on the exit devices (backend-dsr.sh:24). The exit matches tunnels on (local, remote) where remote = EIP, the very address an attacker would forge. Line-by-line reading of `backend-dsr.sh` and what each control does is in 2.6 and RVPN-PFE-001/002/003.
3. Configuration and operational surface. Map parsing uses `std` strict address parsers, rejects short lines, mixed families and bad ports, requires at least one route (ipmap.rs:86-146); duplicates are silently dropped (RVPN-PFE-011). SIGHUP reload is atomic (`RwLock<Arc<IpMap>>`, ipmap.rs:190-196) and keeps the old map on error (main.rs:336-344); the signal handler only sets atomics (:208-214) — async-signal-safe. CLI rejects unknown flags (:125). Unit: root, no `EnvironmentFile`, no `--tunnel`, no sandboxing (RVPN-PFE-005), bounding set likely insufficient for `bpf(2)` (RVPN-PFE-006), `LimitMEMLOCK=infinity` against a 16 MiB umem (main.rs:241-243).
4. Network exposure. Exit: README:93-94 states "DSR exposes the host's entire port space through every EIP"; the allowlist is the sole control and it is non-persistent, non-transactional and name-matched (RVPN-PFE-003); the DSR leg requires the DC not to apply BCP38 egress filtering (backend-dsr.sh:79-81, README:96), which also makes the exit a source-spoofing-capable host if compromised. Front-end: the cloud security group is the only pre-filter; the instance's kernel stack on the bound NIC is unreachable by design; the outer tunnel header is a fixed-TTL, DF=0, sequential-ID GRE flow (packet.rs:243-246, main.rs:550-557) visible only on the cloud-to-DC leg, outside the censor's vantage — not raised as a finding.
5. Data handling. `-d` logs client source IP per packet; `-dd` 64-byte and `-ddd` full hex dumps of client frames; TX dumps include the tunnel addresses (main.rs:528-568) — RVPN-PFE-004. Startup prints the complete map including the exit address (:160-173). Stats (SIGUSR1/60 s) are aggregate counters only. Nothing is written to disk by the program.
6. Platform interaction. Raw `bpf(2)`: XSKMAP of 64 slots (xsk.rs:534-539,680-693), a six-instruction XDP program with GPL licence and 4 KiB verifier log (:712-752); RTM_SETLINK `IFLA_XDP` attach/detach (:767-856) with replace semantics (RVPN-PFE-007); AF_XDP socket `SOCK_CLOEXEC`, `XDP_COPY` bind (:469,518-532); umem 8192 × 2048 B anonymous `MAP_POPULATE` (:452-461); rings 4096 entries. Netlink reply parsing checks `NLMSG_ERROR` only (:834-842) — adequate for an ACK.
7. Memory safety. 31 `unsafe` keyword sites in xsk.rs (including two `unsafe impl Send`), 5 in main.rs. Ring producer/consumer indices use Acquire/Release atomics and masks (:238-345). Packet parsing is bounds-checked before every index (packet.rs:58-67,71-79; main.rs:502). No panic reachable from frame contents was found. Integer handling: lengths bounded by the 2048-byte chunk, u32 checksum accumulator cannot overflow, IP ID wraps by design. The runtime headroom probe (main.rs:376-394) validates the kernel's umem layout once; remaining hygiene gaps in RVPN-PFE-010.
8. Resilience. Single thread, one queue; TX-ring-full drops and recycles (main.rs:579-581); fatal errors exit and systemd restarts (`Restart=always`); on exit `Drop` detaches the program (xsk.rs:651-655); on SIGKILL the socket closes, the XSKMAP entry is removed by the kernel and the program's `XDP_PASS` fallback returns traffic to the kernel stack, which answers with RST/ICMP — fail-visible, not fail-open. Gateway MAC never refreshed (RVPN-PFE-012). Anti-tampering is not applicable to an operator-run root daemon; release profile has LTO and path remapping; no `strip`/`debug` settings (defaults).
9. Dependencies. One crate, vendored, checksum-pinned, no advisories (Appendix B).

What each exit-host control relaxes or mitigates (script line → effect):
- :24 `ip link add ... type gre local <exit> remote <EIP> ttl 64`: tunnel selected by outer (dst, src) only; `ttl` affects only packets the exit would send into the tunnel, which DSR never does. Mitigates nothing; the matching rule is spoofable.
- :28, :40-42 `rp_filter=0` on tunnel devices, `all`, `default`, dummy: disables reverse-path source validation. Effective value is max(all, device) (`IN_DEV_RPFILTER`/`IN_DEV_MAXCONF`), so `all=0` is needed for any per-device 0 to take effect, and `default=0` makes every later-created interface unfiltered. Required because the inner packet's source is any Internet address arriving on a device that is not the return path, and the outer source (EIP) is local. Loose mode (2) satisfies both cases and still rejects sources with no route; 0 is broader than needed. Mitigates nothing.
- :29 `forwarding=0` per tunnel device: ingress-side switch; packets arriving on the device for non-local IPv4 destinations are discarded without ICMP (`ip_route_input_slow` → `ip_error`, which suppresses ICMP for non-forwarding devices). Mitigates the IPv4 relay while the value holds.
- :32-37 dummy device holding each EIP as /32: makes the EIPs local so decapsulated packets are delivered and replies can be sourced from them. Side effect: the EIPs are reachable as local addresses from any interface (weak host model).
- :44-46 `accept_local=1` on `INGRESS_IFACES`: accepts packets whose source is one of the host's own addresses (the outer source after cloud NAT is the EIP, now local). Required for the legitimate path; it equally accepts forged packets claiming any of the host's addresses as source. Mitigates nothing. If `INGRESS_IFACES` is empty nothing works (fails closed).
- :53-57 nft table: see above; policy `accept`, priority -10, so later chains still apply. Does not cover the forward hook, the kernel fallback `gre0` device, or non-tunnel ingress to the EIPs.
- :79-81 BCP38 note: the site must not filter src=EIP on egress; not scriptable; the design depends on it.

## 5. Detailed Findings

### RVPN-PFE-001 — Front-end-to-exit tunnel is unauthenticated (no GRE key, sequence or MAC)
- Severity: Medium. Impact High-tier (bypass of every cloud-side control on the front-end; EIP-to-exit mapping oracle; whatever RVPN-PFE-002/003 leave open). Likelihood Medium: requires forging an outer source — routine for the adversary in the threat model — and knowledge of the exit's address, which DSR otherwise hides. CVSS 3.1: AV:N/AC:H/PR:N/UI:N/S:U/C:L/I:L/A:L (5.6).
- Status: CONFIRMED.
- Location: src/packet.rs:277-287 (`encap_gre_v4`); src/packet.rs:259-272 (`encap_fou_v4`); deploy/backend-dsr.sh:24.
- Description: The GRE header written by the front-end is `[0, 0, 0x08, 0x00]` — no K, S or C bits. The exit's tunnel device is created without `key`, so the kernel selects it on (local, remote) alone, and `remote` is the public EIP, which is exactly the outer source the cloud NAT produces for legitimate traffic. A datagram with a forged outer source equal to an EIP is byte-for-byte indistinguishable from the front-end's. FoU mode is equally unauthenticated (UDP, checksum 0).
- Evidence: packet.rs:283-286 `gre[0] = 0; gre[1] = 0; gre[2..4].copy_from_slice(&ETHERTYPE_IPV4.to_be_bytes());` — backend-dsr.sh:24 `ip link add "$dev" type gre local "$GRE_LOCAL" remote "$remote" ttl 64`.
- Impact: With the current script intact, an injected inner packet is limited by RVPN-PFE-002/003: TCP to an EIP on an allowed port is delivered to the service; other local destinations are dropped; non-local IPv4 is dropped while `forwarding=0` holds. What remains: (a) the exit service is reachable while bypassing the front-end's security groups, flow logs and any rate limiting; (b) an oracle linking EIPs to exits — an inner SYN to EIP X injected at exit Y with inner source = attacker yields a SYN-ACK from X only if Y serves X; (c) the full relay/exposure outcomes whenever the controls in -002/-003 regress; (d) the exit answers proto-47 from any non-EIP source with ICMP port-unreachable (`net/ipv4/ip_gre.c gre_rcv()` reject path), confirming it as a GRE endpoint to a scanner.
- Verification: from a host whose uplink does not enforce BCP38 (lab), `scapy`: `send(IP(src=EIP, dst=EXIT)/GRE()/IP(src=PROBE, dst=EIP)/TCP(dport=80, flags="S"))`; expect a SYN-ACK from EIP at PROBE. On the exit, `nft add rule inet pfe_dsr input meta nftrace set 1` and `nft monitor trace`.
- Recommendation: Stop-gap: add a 32-bit `key` to each exit device and set the K bit and key in `encap_gre_v4` (GRE header becomes 8 bytes; `GRE_HEADROOM` 42). State in the runbook that a key is obscurity against blind injection only — an on-path observer reads it, and blind guessing is 2^32 with the oracle above. Drop proto-47 from non-EIP sources at the physical NIC (`ip protocol gre ip saddr != { EIPs } drop`, which also suppresses the ICMP reply). Target: authenticated encapsulation between front-end and exit — ESP transport mode with NAT-T between the ENI's private address and the exit carrying the GRE, or an equivalent authenticated tunnel the exit can decapsulate in-kernel.
- References: CWE-306, CWE-290, CWE-345; ASVS 4.0.3 V1.9.1, V9.2.2; RFC 2890; BCP38/RFC 2827.

### RVPN-PFE-002 — Relay protection is a per-device IPv4 sysctl that host operations reset; no forward-hook policy; IPv6 uncovered
- Severity: Medium. Impact Critical-tier when the control fails (spoofable relay into any private network the exit routes to — the relay outcome described in 2.6). Likelihood Low–Medium: needs RVPN-PFE-001 injection plus either a change of `net.ipv4.ip_forward` after the tunnel devices exist or global IPv6 forwarding on the exit. CVSS 3.1: AV:N/AC:H/PR:N/UI:N/S:C/C:L/I:L/A:N (5.3).
- Status: CONFIRMED (gap in the script); exploitability depends on host state, verify per host.
- Location: deploy/backend-dsr.sh:29; :53-58 (input chain only); no `net.ipv6` setting anywhere in the script; README.md:79.
- Description: (1) When a write to `net.ipv4.ip_forward` (alias of `conf.all.forwarding`) changes its value, Linux propagates the new value to every interface — `net/ipv4/devinet.c devinet_sysctl_forward()` → `inet_forward_change()`; `ip-sysctl.rst`: "its change resets all configuration parameters to their default state". A write of the unchanged value is a no-op, so the trigger is a flip: `sysctl --system` at boot turning forwarding on after the tunnel devices exist, or a container runtime or VPN bring-up enabling forwarding on a host where it was off. Afterwards `pfe-greN` forwards again. (2) A `type gre` device delivers inner IPv6 (GRE proto 0x86DD) as IPv6. The script sets no IPv6 sysctl; `ip-sysctl.rst` for `conf/all/forwarding`: "IPv4 and IPv6 work differently here; e.g. netfilter must be used to control which interfaces may forward packets". If the exit has IPv6 forwarding on for any other reason, injected inner IPv6 to non-local destinations is forwarded; the input-hook drop at :57 never sees forwarded packets. (3) No forward-hook chain expresses the intended policy independently of sysctl state.
- Evidence: backend-dsr.sh:29 `sysctl -qw "net.ipv4.conf.$dev.forwarding=0"`; :55 `nft add chain inet pfe_dsr input '{ type filter hook input priority -10; policy accept; }'` — the only chain created.
- Impact: Spoofed-source relay from the Internet into the exit's LAN or any tunnelled private network, with the exit's address as the apparent origin.
- Verification: on the exit: `sysctl -w net.ipv4.ip_forward=0; sysctl -w net.ipv4.ip_forward=1; cat /proc/sys/net/ipv4/conf/pfe-gre0/forwarding` (expect `1`: control lost; the toggle is required because writing an unchanged value does not propagate). `sysctl net.ipv6.conf.all.forwarding`. Lab: inject (as in -001) inner IPv4 to a LAN address and inner IPv6 to a routable address; `tcpdump` on the LAN/uplink interface.
- Recommendation: Add `chain forward { type filter hook forward priority -10; policy accept; meta iifkind "gre" drop; meta oifkind "gre" drop; }` to the same table; keep the sysctl as defence in depth; on each tunnel set `net.ipv6.conf.$dev.disable_ipv6=1` and `net.ipv6.conf.$dev.forwarding=0` (inner IPv6 is unsupported, README:105); re-apply per-device sysctls from a udev rule or networkd hook so they survive device re-creation and `ip_forward` flips (or set `net.ipv4.conf.all.forwarding=0` globally if the host does not need to route).
- References: CWE-284, CWE-693, CWE-16; ASVS 4.0.3 V1.14.1, V14.1.1; Linux `Documentation/networking/ip-sysctl.rst`.

## 9. Appendix C — Recommended dynamic test plan
1. Exit allowlist: `nft list table inet pfe_dsr` after `backend-dsr.sh`, after a run with malformed `$EIPS` (expect fail-open, -003), after reboot. `nmap -p- <EIP>` from the Internet expecting only the allowed ports; `nmap -sU` and `ping` expecting silence.
2. Spoofed-outer injection (-001): lab host without BCP38; scapy GRE with outer src=EIP to the exit; inner TCP to EIP:80 (expect SYN-ACK at inner source), inner TCP to EIP:22 (expect drop), inner IPv4 to a LAN address (expect silent drop; repeat after toggling `sysctl -w net.ipv4.ip_forward=0; sysctl -w net.ipv4.ip_forward=1`, expect forwarding — -002), inner IPv6 to a routable address with `net.ipv6.conf.all.forwarding=1` (expect forwarding — -002). GRE from a non-EIP source: expect ICMP port-unreachable (fingerprint).
3. Fallback device: `ip link set gre0 up`; inject from a non-EIP source; expect delivery (-003c).
4. Unit and capabilities (-005/-006): `sysctl kernel.unprivileged_bpf_disabled`; `systemctl start pfe`; journal for `no interface given`, `BPF_PROG_LOAD failed`.
5. Whole-NIC black hole (-007): `ethtool -L <nic> combined 2`; flows hashed to queue 1 to the instance's own address; expect no kernel response; confirm with `bpftool prog show` and `ethtool -S`.
6. Fragments (-008): `nping --udp -p 80 --data-length 2000 <EIP>`; `nstat -az IpReasmFails` on the exit.
7. Reflection (-009): `hping3 -S -p 80 -a <LAN addr> <EIP>`; tcpdump on the exit LAN interface.
8. Logging (-004): start with `-d`, one SYN, `journalctl -u pfe`; measure throughput with and without `-d` (`iperf3` through an EIP) to size the availability effect.
9. TX descriptor validity (-010): sustained load, watch `txInvalid=` in `stats:`.
10. Gateway MAC (-012): change the lab gateway MAC; compare `fwd=` with exit RX.
11. Restart behaviour: `kill -9` pfe, then `tcpdump` on the exit and a client: expect RST/ICMP from the front-end kernel (fail-visible), no forwarding.

## 10. Appendix D — Open questions for the development team
1. What persists the exit configuration today (networkd, ifupdown, a unit running the script)? Is `gre0` guaranteed down?
2. Does any exit host run software that writes `net.ipv4.ip_forward` or enables IPv6 forwarding after `backend-dsr.sh` (container runtime, VPN bring-up)?
3. Is FoU still required by any exit (userspace decapsulator)? If not, can it be removed from the CLI?
4. Is `-d` used on any production front-end, and what is the journald retention there?
5. Is `ethtool -L … combined 1` applied by automation on every front-end, or could a multi-queue NIC be bound?
6. What are the security-group rules on the front NIC, and is proto-47 ingress to exits restricted at the DC edge?
7. Would an authenticated tunnel (ESP/NAT-T or a keyed alternative) be acceptable on the cloud-to-exit leg, and who would own key distribution?
8. Are the EIP /32s expected to be reachable from the exit's LAN side (weak-host), or should that be blocked?
